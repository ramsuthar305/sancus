Chapter 5

We came last.

We put Sancus next to four gateways we admire, gave them the same machine and the same upstream, and measured. Sancus finished fifth of five. The measuring also found a bug and a library that cost us 42 percent.

The race

Each gateway forwarded GET /echo to the same nginx upstream in one Docker network. wrk sent the load from inside that network. Two CPUs, 4 GB, access logs off, median of two 15-second runs. On its own, the upstream answered 344,000 requests a second.

Trust the order more than the digits. In a two-CPU VM the gateway, nginx and wrk fight for the same cores, and Kong scored 58k in one session and 78k in the next. The order held across four sessions.

The first run went badly

Run 1

Sancus managed 11,000 requests a second and returned 502 to one request in five. The logs said EADDRNOTAVAIL: the laptop had run out of ports.

The connection pool to the upstream kept 32 idle connections and threw away the rest. At 100 connections of load, Sancus opened and closed sockets as fast as it could. In eight seconds it left 16,000 of them in TIME_WAIT.

One setting fixed it: keep as many idle connections as busy ones. The 502s stopped. This bug also sat in the production code this project grew out of, where it showed up as the odd unexplained 502 at peak.

Where the time went

With the errors gone, Sancus still did 14,900 requests a second where a bare Node proxy does 42,000. We built four proxies of increasing weight and measured each against the same upstream:

The gateway logic, all of it, cost 4 µs. The proxy library cost 17. We replaced it with a direct http.request pipe and kept Express.

Dropping Express would reach about 35,000 per process. Four workers already pass that, so it waits.

What last place means for you

Per core, Sancus does a seventh of APISIX and half of KrakenD. That is the price of a JavaScript HTTP stack. One process handles about 21,000 requests a second; a four-worker pod handles 30,000 to 37,000. Kettle peaks at 1,800. At that load the gateway adds 0.3 ms at the median and the team's time goes to the product.

If one node of yours has to carry 50,000 a second, the right door is APISIX or Kong.

Run it yourself

brew install wrk oha
npm ci && npm run build
npm run bench                     # every feature; results in tests/bench/results/
docker build -t sancus:slim .
tests/bench/compare/compare.sh    # Sancus against Traefik, Kong, APISIX, KrakenD

Run it on a Linux machine with dedicated cores and send a pull request with your numbers. Both scripts print the exact commands and stop on any non-2xx response.

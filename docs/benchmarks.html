Chapter 5

How fast it is.

Kettle peaks at 1,800 requests a second at dinner time. Before putting Sancus in front of checkout, Asha wanted to know what the gateway costs per request, what each feature adds, and how much headroom there is. These are the numbers, and the script to reproduce them.

21,398requests a second, one process
37,130requests a second, four workers, auth + limit + cache
0.3 msadded at the median, at a steady 2,000 req/s
0errors across every run

How we measured

One gateway process on an Apple M4 laptop, Node 24, a local Redis, and a four-process Node upstream that answers 220,000 requests a second on its own, so the upstream is never the bottleneck. wrk sends load over 100 connections for 15 seconds, after a 5-second warm-up. We report the median of two runs. Any non-2xx response fails the run.

"As shipped" means the default config, with the access log and the per-IP limiter on. "Tuned" means LOG_LEVEL=warn with the per-IP limiter off, the usual setting behind a load balancer that already protects per IP.

Read it top to bottom as a price list. The access log at info costs about 20 percent. A Redis-backed rate limit or a cached token check costs about 13 percent each. A cache hit is the fastest path because the upstream drops out of the picture. Four workers add 1.4 to 1.7 times on this laptop, where wrk competes for the same cores; on a dedicated machine they scale closer to the core count.

What the first run found

Run 1

Sancus returned 502 to one request in five. The logs said EADDRNOTAVAIL: the machine had run out of ports.

The connection pool to the upstream kept 32 idle connections and threw away the rest. Under load, Sancus opened and closed sockets as fast as it could, and left 16,000 of them in TIME_WAIT in eight seconds.

One setting fixed it: keep as many idle connections as busy ones. Every table on this page has zero errors.

Where the time went, and what we changed

To see which part of a request cost the most, we measured four proxies of increasing weight against the same upstream.

Stackreq/sCPU per request

Sancus with every feature, before the change14,90067 µs

All of the gateway's own logic cost 4 µs. The proxy library cost 17. We replaced it with a direct http.request pipe.

Sizing for your traffic

Your peakStart with
up to 5,000 req/s2 pods, 1 CPU each, WORKERS=1 (two for availability)
5,000 to 20,000 req/s2 to 3 pods, 2 CPU each, WORKERS=2
20,000 to 60,000 req/spods with 4 CPU and WORKERS=4, scaled by the HPA on CPU

Leave headroom: plan for half the measured maximum, and turn on caching for the routes that repeat. Kettle runs two pods with one CPU each and sits under 10 percent CPU at dinner.

Run it yourself

brew install wrk oha      # or your package manager
npm ci && npm run build
npm run bench             # results in tests/bench/results/

The script starts its own upstream and gateways, prints the exact wrk and oha commands, and stops on any non-2xx response. Run it on your own hardware and you have numbers for your capacity plan.

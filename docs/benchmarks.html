How fast it is.

Kettle peaks at 1,800 requests a second at dinner time. Before putting Sancus in front of checkout, Asha wanted to know what the gateway costs per request, what each feature adds, and how much headroom there is. These are the numbers, and the script to reproduce them.

27,452requests a second, one process
47,094requests a second, four workers, auth + limit + cache
0.3 msadded at the median, at a steady 2,000 req/s
0errors across every run

How we measured

One gateway process on an Apple M4 laptop, Node 24 with --max-old-space-size=256 as in the image, a local Redis, and a four-process Node upstream that answers 220,000 requests a second on its own, so the upstream is never the bottleneck. wrk sends load over 100 connections for 15 seconds, after a 5-second warm-up. We report the median of two runs. Any non-2xx response fails the run.

"As shipped" means the default config, with the access log and the per-IP limiter on. "Tuned" means LOG_LEVEL=warn with the per-IP limiter off, the usual setting behind a load balancer that already protects per IP.

Read it top to bottom as a price list. The access log at info and the per-IP limiter together cost about 23 percent. A Redis-backed rate limit costs about 15 percent and a cached token check about 19. A cache hit is the fastest path because the upstream drops out of the picture. Four workers add 1.3 to 1.6 times on this laptop, where wrk competes for the same cores; on a dedicated machine they scale closer to the core count.

At a steady 2,000 a second

The table above pushes the gateway to its limit, so most of that latency is queueing. Real traffic is steadier. Here oha holds the rate at 2,000 requests a second.

The upstream on its own answers in 0.12 ms. Through one Sancus process it takes 0.38 ms, so the gateway adds about 0.3 ms at the median. The p99.9 spikes are garbage collection pauses in V8; more workers spread them out.

Sizing for your traffic

Your peakStart with
up to 5,000 req/s2 pods, 1 CPU each, WORKERS=1 (two for availability)
5,000 to 20,000 req/s2 to 3 pods, 2 CPU each, WORKERS=2
20,000 to 60,000 req/spods with 4 CPU and WORKERS=4, scaled by the HPA on CPU

Leave headroom: plan for half the measured maximum, and turn on caching for the routes that repeat. Kettle runs two pods with one CPU each and sits under 10 percent CPU at dinner.

Run it yourself

brew install wrk oha      # or your package manager
npm ci && npm run build
DURATION=15 npm run bench # results in tests/bench/results/

The script starts its own upstream and gateways, prints the exact wrk and oha commands, and stops on any non-2xx response. Run it on your own hardware and you have numbers for your capacity plan.

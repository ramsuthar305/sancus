Upstreams and failure

A service can have several nodes. Sancus spreads requests across them, steps around the ones that fail, gives up on the slow ones, and stops calling a service that keeps failing.

Nodes

service:
  name: users
  nodes: [http://users-a:8080, http://users-b:8080]
  retries: 1
  timeout: 5000
  circuitBreaker: { volumeThreshold: 10, errorThresholdPercentage: 50, resetTimeout: 30000 }

Requests go round-robin. A node that refuses connections, or whose name does not resolve, is marked down for UPSTREAM_UNHEALTHY_TTL_MS (30 s) and skipped. If every node is down, Sancus tries anyway rather than fail without asking. Connections to each node are kept alive in a pool of UPSTREAM_MAX_SOCKETS per worker.

Retries

retries is the number of extra attempts after a connection error, each on the next node. Only GET, HEAD and OPTIONS retry, because a POST that reached the upstream before the connection dropped may have done its work. A 5xx from the upstream is a response, not a connection error, and is never retried.

Timeouts

timeout is how long to wait for the upstream's response headers. Past it the client gets a 504 and the upstream request is cancelled. Set it below your load balancer's idle timeout so the client hears from Sancus rather than from the balancer.

Circuit breaker

With a circuitBreaker block, Sancus counts each proxied call to the service over a rolling ten-second window. Once at least volumeThreshold calls happened and more than errorThresholdPercentage of them failed, the breaker opens. Failures are connection errors, timeouts and 5xx responses. While open, callers get a 503 with Retry-After at once and the service gets a rest. After resetTimeout milliseconds one request is let through; if it succeeds the breaker closes.

The breaker is per service, per gateway worker. It is not shared through Redis, so with four workers each one decides on its own view of the traffic.

Every one of these also sends an alert to ALERT_WEBHOOK_URL if you set one, at most once a minute per service and error.

Streaming

Bodies stream in both directions. Server-Sent Events pass through without buffering or compression, and the gateway stops the upstream request when the client disconnects. Multipart uploads are parsed, checked against a size and type list, and re-sent.

Hot reload

Save a file in api_configs/ and Sancus validates it and swaps the routing table in place. A file that fails validation is logged, counted in sancus_config_reloads_total{status="error"}, and ignored. The previous config keeps serving.

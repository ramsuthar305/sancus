Chapter 1

The door your services share.

Sancus is an API gateway you set up in an afternoon. One YAML file per service. It checks the token, counts the request, answers from cache when it can, and forwards the rest.

A night at Kettle

Kettle is a made-up food delivery startup. You will follow its team through these pages. It runs three services: menu, orders and search. Asha is on call.

02:14

Asha's phone goes off. Checkout is failing. A partner's sync script has a bug and is calling the API in a loop, 900 requests a second.

The menu service shrugs it off. Someone gave menu a rate limiter last spring. Orders has none; the ticket to add one has been open since March. The script hits orders too, and orders runs out of database connections. Checkout goes down with it.

03:05

Asha blocks the partner's key by hand and checkout recovers. Then Asha opens the three codebases side by side.

Menu checks tokens with a library. Orders checks them with a copy of that library from two versions ago. Search caches in memory, so each pod has its own cache. Three services, three front doors, three sets of locks, and nobody holds the list.

The fix the team settled on the next morning was one door in front of all three. That door is Sancus.

Why a shared door

Each of your services has jobs that have nothing to do with what it is for. It checks the token. It decides if a caller is sending too much. It caches the answers people ask for over and over. It tags requests so you can trace them in the logs. When every service does these jobs itself, each one does them a little differently, and the gaps only show up at 2 a.m.

Sancus takes those jobs out of your services and does them once, at the front. Your services get a request that already carries a verified user id and a request id, and that already fits inside its limit. The code you delete is code nobody has to keep in sync again.

When you need Sancus

You run more than one service

Two or three services is where copied auth and limiter code starts to drift. One config in front of all of them stops the drift.

One caller can hurt everyone

A partner script, a buggy app release or a scraper. Per-user and per-IP limits at the door stop it before your database feels it.

People ask the same thing again and again

Feeds, menus, search results, today's challenge. A shared cache answers them without your service.

Phones or partners call your API

You want one public address, standard rate-limit headers and clean error codes.

You can't answer "what happened to request X?"

One request id through every log line, and metrics per service and route.

Why we built it when good gateways already existed

Sancus started as a small open-source project and grew up in production, in front of a product with a handful of Node services and a team of a few engineers. We tried the established gateways first. Kong, APISIX, Traefik and KrakenD are good software. Each one asked for something our team did not have to spare.

  • They wanted their own infrastructure. Kong's full feature set expects a database or a control plane. APISIX keeps its config in etcd. That meant one more stateful system to run, back up and learn, for a team that already ran Redis and nothing else.
  • The features we needed sat in paid editions. A sliding-window rate limit shared through Redis, and a response cache stored in Redis, are Enterprise features in Kong. A Redis-backed global rate limit is Enterprise in KrakenD. Traefik has no response cache in its open-source build. We needed all of those on day one.
  • Nobody offered stale-while-revalidate. Our slowest endpoints were the ones users hit most. We wanted to serve a slightly old answer at once and refresh it in the background. The open-source caches we found only knew fresh or expired.
  • Extending them meant a language we did not write. Custom logic in Kong and APISIX is Lua, in KrakenD and Traefik it is Go. Our team wrote TypeScript. A rule we could write in ten lines of JavaScript would have been a small project in another language.
  • Config lived in the wrong place for us. We wanted each service's routes in one file that its owners change in a pull request, checked by CI, and picked up without a restart. Admin APIs and one large config file did not fit that.
  • We had one odd requirement. Some routes had to refuse requests from specific regions. No gateway we looked at shipped geo-fencing in its open-source build.

So we wrote the smallest gateway that did those things, in the language the team already used, on the one database it already ran. It trades raw throughput per core for that: chapter 5 has the numbers, and they cover most products with room to spare. If your needs match the list above, Sancus fits. If one gateway node has to carry tens of thousands of requests a second, or you already run a gateway you are happy with, keep that one.

What the door does

Each request walks six stations. Any station can stop it. A cache hit stops at station five and never reaches your service. Chapter 3 follows one request through all six, header by header.

The file that would have saved the night

service:
  name: orders
  nodes: [http://orders-a:8080, http://orders-b:8080]
  timeout: 5000
apis:
  - name: Orders
    routes:
      - path: /v1/orders/{int:id}
        methods: [GET]
      - path: /v1/orders
        methods: [POST]
        rateLimit: { perMinute: 30, key: USER }

That is api_configs/orders.yml. Every route needs a valid token because none of them say bypass: [AUTH]. Creating an order is capped at 30 a minute per user. The partner's loop gets 429 at the door, and the orders database never hears about it.

What else is behind the door

Your auth, not ours

Sancus sends the token to the verifier you already run. A 2xx with a user id means valid. The id reaches your service as a header, and your service stops parsing tokens.

Limits every pod agrees on

Counts live in Redis. Add a second gateway pod and nobody gets double the quota. Clients get X-RateLimit-* and Retry-After.

A shared cache

LRU, LFU or stale-while-revalidate per route, with ETags and 304s.

Failure at the edge

Several nodes, retries, timeouts and a circuit breaker.

Your own rules

A policy is a small JavaScript file you name in YAML.

Built to run

Readiness that checks config and Redis, Prometheus metrics, JSON logs with a request id on every line, a clean drain on SIGTERM, an 80 MB image.

Reloads on save

Edit a YAML file and the next request uses it. A broken file is refused.

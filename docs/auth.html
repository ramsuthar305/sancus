Authentication.

Sancus does not check tokens itself. It calls a verifier you run and trusts the answer. This is the same contract Traefik calls ForwardAuth and APISIX calls forward-auth, so a verifier written for one of those works here.

09:25, hour one

Asha deleted forty lines of token checking from orders. The five steps below replaced them.

The contract

  1. A request arrives for a route without bypass: [AUTH]. Sancus reads the Authorization header.
  2. Sancus calls AUTH_URL + AUTH_VERIFY_PATH. The token goes in a JSON body field or a header, your choice. The call also carries X-Forwarded-Method, -Proto, -Host, -Uri, -For, and whichever client headers you list in AUTH_REQUEST_HEADERS.
  3. A 2xx answer with the user id at AUTH_USER_ID_FIELD means valid. Sancus forwards the id as X-AUTHORIZED-FOR-ID and copies any response headers you list in AUTH_UPSTREAM_HEADERS onto the upstream request. The result is cached in Redis for AUTH_CACHE_TTL seconds, keyed by a sha256 of the token.
  4. Any other status goes back to the client as is: same status, same body, plus response headers you list in AUTH_CLIENT_HEADERS.
  5. If the verifier is unreachable, the client gets AUTH_STATUS_ON_ERROR (403). Set AUTH_FAIL_OPEN=true to let requests through anonymously instead.

Three verifiers

A JSON endpoint that takes the token in the body

This is the default. Set AUTH_URL and nothing else. Sancus posts {"token": "Bearer ..."} to /v1/verify/token and reads id from the answer.

A "who am I" endpoint that reads the bearer header

AUTH_URL=https://auth.internal
AUTH_VERIFY_PATH=/me
AUTH_VERIFY_METHOD=GET
AUTH_TOKEN_IN=header
AUTH_USER_ID_FIELD=user.uuid
AUTH_UPSTREAM_HEADERS=x-user-role,x-tenant

OAuth2 token introspection (RFC 7662)

Introspection endpoints answer 200 for every well-formed request and put active: true or false in the body. Sancus treats 2xx as valid, so front the endpoint with a five-line service that returns 401 when active is false. The demo's services/auth.js is a template.

Public routes that still know who you are

A feed that shows more to logged-in users is public but personal. Put bypass: [AUTH] and resolveUser: true on it. Requests without a token pass through anonymously. Requests with a valid token get the user id forwarded. A bad token is ignored rather than rejected.

What the upstream receives

HeaderValue
X-AUTHORIZED-FOR-IDthe user id from the verifier
headers in AUTH_UPSTREAM_HEADERScopied from the verifier's response, for roles or tenants
X-Request-Idthe request id, for logs
X-Forwarded-For, -Proto, -Hostthe client's address and original host

Your services never see the token unless you list authorization in a route's headers.add. They trust the gateway's user id header, so make sure nothing but the gateway can reach them.

Rate limiting

Two limiters. A global per-IP token bucket protects the gateway from any single address. Per-route sliding windows protect your services from any single user, key or IP. Both count in Redis, so every gateway pod sees the same numbers.

Per route

rateLimit:
  perMinute: 120
  perDay: 5000
  key: USER_OR_IP     # IP | USER | API_KEY | USER_OR_IP | IP_USER
  group: search       # optional: share one quota across routes with the same group
  hideHeaders: false  # true: no X-RateLimit-* headers to the client
KeyCounts per
IPclient address, as resolved by TRUST_PROXY
USERthe user id from auth; falls back to IP when anonymous
API_KEYthe X-API-Key header; falls back to IP
USER_OR_IPuser when logged in, IP otherwise
IP_USERthe pair, so one user on two devices gets two quotas

Each window is a sliding log in a Redis sorted set, run as one Lua script per window. The day window runs first, so a daily rejection does not consume a minute token.

Headers the client sees

HeaderExample
X-RateLimit-Limit, -Remaining, -Reset120, 17, 42
RateLimit-Limit, -Remaining, -Reset120, 120;w=60 / 17 / 42
Retry-After on 42942

Both families, because clients written for Kong read one and clients written for Envoy read the other. Reset values are seconds until the window frees up. When two windows apply, the headers describe the tighter one.

The global IP bucket

Every request first passes a token bucket per client IP: IP_RATE_LIMIT_CAPACITY tokens (200), refilled at IP_RATE_LIMIT_REFILL_RATE a second (5). An address that gets 429 twenty times in a minute is blocked for fifteen minutes with a 403. Addresses in TRUSTED_IPS skip both limiters.

This limiter keys on the client IP. Behind a load balancer that IP comes from X-Forwarded-For, which Sancus only believes when TRUST_PROXY says the peer is a proxy. Get that wrong and every user shares one bucket. Sancus refuses to start with TRUST_PROXY=false while this limiter is on. Set IP_RATE_LIMIT_ENABLED=false if your balancer already does per-IP protection.

Order matters

A cache hit is answered before the rate limiter runs. A hit costs no upstream work, so it is not counted. Put limits on routes that are expensive, not on routes that are cached.

When Redis is down

Requests go through, with no rate-limit headers, and a warning in the log. A Redis outage should not take your API with it.

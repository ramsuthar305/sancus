Chapter 2

Hour one.

The morning after, Asha blocks out one hour to put Sancus in front of orders. You can follow along on your laptop. You need Docker, or Node 18 and Redis.

09:00

Asha clones the repo and starts it with Docker Compose. The compose file brings up the gateway and a Redis next to it.

git clone https://github.com/ramsuthar305/sancus.git && cd sancus
docker compose up
sancus-1 | {"level":30,"msg":"RouteRegistry: loaded 3 routes for service \"your_service_name\""} sancus-1 | {"level":30,"msg":"geo-fence disabled (no polygons in GEOFENCE_FILE)"} sancus-1 | {"level":30,"msg":"Redis connection ready"} sancus-1 | {"level":30,"port":3000,"msg":"Sancus gateway listening"}
curl localhost:3000/health/ready
{"status":"UP","configLoadedAt":"2026-09-26T09:01:12.402Z"}

/health/ready says UP only once the config has loaded and Redis answers. Kubernetes will ask the same question later.

09:10

Asha writes orders.yml, the twelve lines from chapter 1, and points ORDERS at the running service. No restart. Sancus reloads when the file is saved.

curl -i localhost:3000/api/orders/v1/orders/881 -H "Authorization: Bearer $TOKEN"
HTTP/1.1 200 OK X-Request-Id: 7f3a0c2e-51d4-4b8e-9d1a-2c6f0e7b3a19 content-type: application/json {"id":881,"status":"out_for_delivery"}

The request went /api/orders/v1/orders/881 in, /v1/orders/881 out. Sancus strips /api/<service> and forwards the rest.

09:25

The token check still runs inside orders, so every request is now checked twice. Asha points Sancus at the token endpoint the team already has, then deletes forty lines from orders.

AUTH_URL=http://auth.internal:8001    # POST /v1/verify/token {"token": "..."} -> {"id": ...}
Before, in each service
app.use(async (req, res, next) => {
  const token = req.headers.authorization;
  if (!token) return res.status(401).end();
  const r = await fetch(AUTH + '/v1/verify/token', {
    method: 'POST', body: JSON.stringify({ token }),
  });
  if (!r.ok) return res.status(401).end();
  req.user = (await r.json()).id;
  next();
});
After, in each service
// Sancus verified the token already.
app.use((req, _res, next) => {
  req.user = req.headers['x-authorized-for-id'];
  next();
});

Your verifier might want the token in a header, or return the id somewhere else. Five settings cover that. Authentication has the contract.

09:40

Asha reads the one warning in the README twice.

Set TRUST_PROXY to match your network before you go live. Sancus learns the client address from X-Forwarded-For, and only trusts that header when the request came from a proxy it knows. The default trusts private addresses, where a load balancer or ingress sits inside a VPC. If your proxy has a public address, list its ranges. If you set TRUST_PROXY=false behind a balancer, every user looks like the balancer, shares one rate-limit bucket, and the site throttles itself. Sancus refuses to start in that setup.

09:55

Staging. The repo has a kustomize folder with the pieces a cluster needs.

kubectl apply -k k8s/

You get a ConfigMap for settings, an example Secret, a Deployment with readiness on /health/ready, limits, an HPA and a disruption budget. Change the image tag, the host and the upstream URLs. Running in production covers what to watch after that.

Without Docker

npm ci && npm run build
npm run check        # validate api_configs/ without starting
npm start            # or npm run dev while you change the gateway itself

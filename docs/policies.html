Policies

A policy is a named middleware you configure from YAML. Sancus ships one, ip-restriction. You write the rest as files in policies/, and reference them by name on a service or a route.

Using one

service:
  name: admin
  nodes: [http://admin:8080]
  policies:
    ip-restriction: { allow: [10.0.0.0/8, 203.0.113.7], deny: [] }
apis:
  - name: Imports
    routes:
      - path: /v1/import
        methods: [POST]
        policies:
          require-header: { header: X-Idempotency-Key }

Service policies run first, then route policies, each set in priority order. A policy that answers the request ends it there. Sancus validates the config against the policy's schema when the file loads, so a typo is a startup error rather than a runtime surprise.

Writing one

// policies/require-header.js
module.exports = {
  name: 'require-header',
  priority: 10,             // higher runs first
  schema: { type: 'object', required: ['header'], properties: { header: { type: 'string' } } },
  create: ({ header }) => (req, res, next) =>
    req.headers[header.toLowerCase()] ? next() : res.status(400).json({ message: `missing ${{header}}` }),
};

create receives the config from YAML and returns an Express middleware. Anything Express can do, a policy can do: read headers, set headers, reject, redirect, call another service. The module can also export an array of policies.

ip-restriction

allow and deny take addresses or CIDR ranges. Deny wins. A non-empty allow list rejects anything not on it. Matching uses Node's built-in BlockList, so IPv6 works.

Ideas

  • A maintenance switch that answers 503 for one service while you deploy it.
  • A header that must match a tenant id from the auth response, forwarded via AUTH_UPSTREAM_HEADERS.
  • A canary that sends one request in ten to a different node list.
  • A body size cap on upload routes.

/routes lists the policies that are loaded.

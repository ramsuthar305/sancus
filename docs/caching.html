Caching.

Add a cache block to a GET route and Sancus stores the response in Redis. Hits skip auth, rate limits and the upstream. The headers are the ones every CDN uses, so your clients and your monitoring already understand them.

Dinner time, week two

Search took 900 ms per query and got 400 queries a second, most of them repeats. The team had a Redis cache inside search, written in a hurry, keyed on the wrong thing, and never invalidated.

Before, in search
const hit = await redis.get('nearby:' + req.query.area);
if (hit) return res.json(JSON.parse(hit));
const rows = await slowNearbyQuery(req.query);
await redis.set('nearby:' + req.query.area,
  JSON.stringify(rows), 'EX', 120);
res.json(rows);   // forgot language, forgot ETag
After, in search.yml
- path: /v1/nearby
  methods: [GET]
  bypass: [AUTH]
  cache:
    strategy: SWR
    ttl: 120
    key: PATH_QUERY
    varyHeaders: [Accept-Language]

Config

cache:
  strategy: SWR              # LRU | LFU | SWR
  ttl: 300                   # seconds in Redis
  key: PATH_QUERY            # PATH | PATH_QUERY | PATH_QUERY_USER
  browserTtl: 60             # optional: emits Cache-Control to clients
  varyHeaders: [Accept-Language]
  statusCodes: [200, 404]    # default 200, 301, 404
StrategyBehaviour
LRUPlain TTL. Redis evicts old entries under memory pressure.
LFUTracks how often each entry is read and evicts the least-read ones past CACHE_LFU_MAX_ENTRIES.
SWRStale-while-revalidate. In the last quarter of the TTL an entry is served at once as STALE and refreshed in the background. Users never wait for the refresh.
KeyOne entry per
PATHpath
PATH_QUERYpath and query string
PATH_QUERY_USERpath, query and user id. Responses are marked private and Vary: Authorization.

What gets stored

Only GET and HEAD. Only the statuses in statusCodes. Never a response with Cache-Control: no-store or private, and never one with Set-Cookie. A request with Cache-Control: no-cache skips the lookup. Bodies are stored as bytes, so compressed responses come back intact.

Headers

HeaderMeaning
X-Cache-StatusHIT, MISS, STALE (served stale, refreshing) or BYPASS (not cacheable)
X-Cache-Keya short hash of the key, to match requests to entries without leaking the key
Ageseconds since the entry was stored
ETaga hash of the body; send it back as If-None-Match for a 304
Cache-Controlonly with browserTtl: public, max-age=N, or private for per-user keys, plus stale-while-revalidate for SWR
Varythe headers in varyHeaders, plus Authorization for per-user keys

Purging

curl -X DELETE localhost:3000/cache/users -H 'Authorization: Bearer $ADMIN_TOKEN'

Drops every entry for one service. There is no per-key purge; use a short TTL or SWR for data that changes often.

Choosing a TTL

Ask how stale is acceptable, not how often the data changes. A product list that updates hourly is fine at five minutes. A price is not. SWR is the safe default for anything users read a lot: the upstream sees one request per TTL, and users see fresh data one request later.
